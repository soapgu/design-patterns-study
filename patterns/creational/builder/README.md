## 一句话理解

生成器把复杂对象的构造拆成一组可组合的步骤，使同一套构造流程能够生成不同形式的产品，并避免把大量可选
参数和组装细节塞进构造函数或客户端代码。

## 第一阶段：概念理解

### 它要解决什么问题

当一个对象包含很多部件、可选配置或固定装配顺序时，直接构造容易出现以下问题：

- 构造函数参数过多，调用处难以理解每个值的含义。
- 为不同参数组合创建大量重载或子类，组合数量快速膨胀。
- 分散在客户端各处的组装步骤容易遗漏、顺序错误或重复。
- 产品业务逻辑与复杂构造逻辑混在一起，变化原因互相干扰。
- 对象尚未组装完整就暴露给外部，形成无效的中间状态。

生成器把“如何一步步构造”移到独立对象中。客户端可以选择需要的步骤；常用的步骤顺序还可以交给主管统一
编排。

### 核心意图

生成器关注的不是“选择哪个具体类”，而是“一个复杂结果如何经过多个步骤形成”。它将构造过程与最终产品的
表示分离，让相似流程能够生产不同配置，甚至不同类型的结果。

### 参与者与职责

| 角色 | 职责 |
| --- | --- |
| `Builder`（生成器） | 声明各具体生成器都理解的构造步骤。 |
| `ConcreteBuilder`（具体生成器） | 实现步骤、维护构造中的产品，并提供取得结果的方式。 |
| `Product`（产品） | 最终构造结果；不同生成器的产品不一定属于同一继承体系。 |
| `Director`（主管） | 封装步骤顺序和常用构造方案；它是可选角色。 |
| `Client`（客户端） | 选择具体生成器，可交给主管编排，也可直接控制步骤。 |

### 协作流程

1. 客户端创建具体生成器。
2. 客户端将生成器交给主管，或自行调用构造步骤。
3. 生成器在内部逐步形成产品，不向外暴露未完成结果。
4. 构造完成后，客户端从具体生成器取得产品。
5. 若生成器需要复用，则显式重置，或在取出产品后自动重置。

主管只知道构造步骤及其顺序，不必知道具体产品类型。因为不同生成器可能生成完全不同的产品，取得结果的方法
通常属于具体生成器，而不是主管或通用生成器接口。

### 主管是否必需

不是。主管的价值是保存可复用的“配方”，例如标准配置、豪华配置或精简配置。如果构造顺序简单、只在一个
地方使用，客户端直接调用生成器可能更清晰。不要为了类图完整而强行创建主管。

### 适用场景

- 构造函数存在大量可选参数，或出现层层重载的“伸缩构造函数”。
- 一个对象必须经过多个有顺序或有条件的步骤才能安全完成。
- 希望用相似步骤创建不同配置或不同表示的产品。
- 构造组合树、配置对象、请求对象或其他层次复杂的结构。
- 常用构造流程需要命名、复用或集中维护。

### 不适用场景

- 对象只有少量必填字段，直接构造已经清晰。
- 所谓步骤只是简单字段赋值，没有顺序、校验或组合价值。
- 产品天然适合不可变记录、命名参数或对象初始化器，语言能力已经足够表达。
- 增加生成器、具体生成器和主管的维护成本高于构造本身的复杂度。

### 优点

- 可以分步、延迟或有条件地构造复杂对象。
- 将复杂构造与产品业务逻辑分离，职责更集中。
- 同一构造流程可以复用于不同产品配置或表示。
- 可以在返回结果前统一检查完整性，减少半成品泄漏。
- 主管可以为常用构造方案提供清晰名称。

### 缺点与代价

- 会增加接口、具体生成器和可选主管等类型，整体结构更复杂。
- 可选步骤之间若存在隐含依赖，调用顺序仍可能难以理解。
- 可变生成器包含中间状态，复用、重置和并发使用需要明确约束。
- 流式 API 虽然易读，但可能掩盖必填步骤缺失，最终仍需校验。

### 容易混淆的概念

#### 生成器与工厂方法

- 工厂方法主要通过多态决定创建哪一种产品，通常一次调用就返回结果。
- 生成器主要组织复杂产品的多个构造步骤，结果通常在最后才取得。
- 工厂方法的变化点是“具体产品类型”；生成器的变化点是“构造步骤、顺序和最终表示”。

#### 生成器与抽象工厂

- 抽象工厂用于创建一族相互匹配的产品，调用各工厂方法后立即得到产品。
- 生成器围绕一个连续构造过程工作，允许在取得结果前执行多个步骤。
- 不同生成器甚至可以用同一流程生成没有共同父类型的结果。

#### 生成器与流式 API

返回 `this` 的链式方法只是调用风格，不自动等于生成器模式。只有当这些调用共同承担复杂对象的分步构造、
隔离构造细节并在最后交付结果时，才体现生成器的核心意图。

### 语言能力带来的简化

| 语言 | 可用能力 | 仍需警惕 |
| --- | --- | --- |
| C# | 命名参数、可选参数、对象初始化器、`record`、`init` 属性 | 这些能力能减少简单生成器，但无法自动封装复杂顺序与校验。 |
| TypeScript | 对象字面量、可选属性、结构化类型、泛型与分阶段类型 | 很多配置对象无需经典类层次；必填步骤可尝试在类型层表达。 |
| JavaScript | 对象展开、默认参数、闭包和函数组合 | 缺少静态契约，必须通过运行时校验防止不完整产品。 |

### 设计原则

- **单一职责**：将复杂构造从产品业务行为中分离。
- **开闭原则**：增加新的具体生成器或构造配方，尽量不修改已有流程。
- **依赖倒置**：主管依赖生成器步骤抽象，而不依赖具体产品。
- **封装变化**：把易变的组装细节、步骤顺序和产品表示隔离起来。

### 自检问题

1. 为什么生成器不只是“换一种方式写构造函数”？
2. 什么时候需要主管，什么时候客户端直接调用步骤更简单？
3. 为什么取得结果的方法不一定适合放在通用生成器接口中？
4. 自动重置生成器和显式重置各有什么风险？
5. 当前语言的对象初始化能力是否已经足够，经典生成器是否会过度设计？
6. 如何保证必填步骤完成后才允许取得产品？

### 代码角色与概念对应

| 模式角色 | C# 类型 | 作用 |
| --- | --- | --- |
| 生成器 | `IBuilder` | 声明构造 A、B、C 三个部件的共同步骤。 |
| 具体生成器 | `ConcreteBuilder` | 维护构造中的产品，实现步骤并在返回结果后重置。 |
| 产品 | `Product` | 保存最终部件，并通过只读集合暴露构造结果。 |
| 主管 | `Director` | 封装最小产品和完整产品两种可复用配方。 |
| 客户端 | `Program` | 选择生成器与配方，也可直接控制构造步骤。 |

官网示例通过 `Director.Builder` 属性保存生成器。本仓库改为由每个构造方法接收 `IBuilder`，让主管保持无状态，
也更直观地展示同一配方可以作用于不同生成器。

TypeScript 的结构化类型允许普通对象只要满足 `Builder` 接口就接入主管，无需显式声明 `implements`。
JavaScript 版本通过 JSDoc 描述同样的最小结构，使 IDE 能提供补全，但实际约束仍在运行时。

### 自动化测试

每种语言均有 5 个测试，覆盖：

- 客户端能够自由组合构造步骤。
- 主管能够生成最小产品和完整产品，并保持规定顺序。
- 取得产品后生成器自动重置，之前返回的结果不受后续构造影响。
- 自定义生成器可以通过 `IBuilder` 接入同一主管流程。

测试关注参与者协作和状态边界，不验证控制台固定排版，也不制造与模式无关的异常场景。
